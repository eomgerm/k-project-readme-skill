# 블록 카탈로그

한국 부트캠프·동아리 README 25개에서 반복된 마크업이다. 골격만 가져다 쓰고 문구는 새로 쓴다.
블록 조합 규칙과 조건은 `SKILL.md` 6번에 있다. **블록 ID는 이 문서 안에서만 쓰는 식별자다** —
사용자에게 보이는 텍스트에 넣지 않는다.

## L0 히어로

### H1 배너

```html
<img src="TODO_배너_이미지" alt="{서비스명}" width="100%"/>
```

### H2 링크줄

가운데정렬. 팀이 실제로 쓰는 곳만 넣는다. 링크가 2개 이하면 이 블록을 생략하고 S1에 문장으로 녹인다.

```html
<p align="center">
  <a href="{배포주소}">
    <img src="TODO_바로가기_버튼" alt="{서비스명} 바로가기" width="250"/>
  </a>
  <br/><br/>
  <a href="{노션}">팀 노션</a>
  &nbsp;|&nbsp;
  <a href="{위키}">개발 위키</a>
  &nbsp;|&nbsp;
  <a href="{피그마}">디자인</a>
</p>
```

**변형 — 링크 뱃지형.** 텍스트 대신 뱃지로 쓴다. 마크업은 `badges.md`의 "히어로 링크 뱃지".

### H3 스토어 링크 (앱 레포)

로고를 왼쪽에 띄우고 제목과 스토어 링크를 붙인다.

```html
# {서비스명} <a href="{앱스토어_링크}"><img src="TODO_앱_로고" align="left" width="100"/></a>
```

스토어 링크를 못 받았으면 `<a>`를 벗기고 로고와 제목만 남긴다. 부트캠프 앱 저장소는
미출시가 표준이라 이쪽이 오히려 흔하다.

### H4 CI 상태 뱃지 (CI 있음)

배너 바로 아래 한 줄. `{워크플로_파일명}`에는 확장자까지 넣는다 (`Build.yaml`, `ci.yml`). `.yaml`인데 `.yml`로 적으면
404가 떠서 깨진 이미지로 남는다.

```markdown
[![CI](https://github.com/{owner}/{repo}/actions/workflows/{워크플로_파일명}/badge.svg)](https://github.com/{owner}/{repo}/actions)
```

## L1 요약

### S1 소개 + 불릿

한 줄 캐치프레이즈 뒤에 불릿. 개수는 2~5개로, 내용에 따라 다르게.

```markdown
## ✍🏻 서비스 소개

<img src="TODO_소개_이미지" alt="{서비스명} 소개"/>

- {서비스명}은 {한 줄 정의}입니다.
- {특징 하나}
- {특징 둘, 여기는 길게 두 줄로 써도 된다}
```

### S2 개발 기간

날짜만 코드로 감싸 한 줄. 표나 타임라인으로 부풀리지 않는다.

```markdown
### 프로젝트 기간

`2025.10.28 ~ 2025.12.06`
```

### S3 목차 (본문 8KB 초과)

앵커는 소문자, 공백은 `-`, 이모지는 제거하고 앞에 `-`가 남는다.

```markdown
- [✍🏻 서비스 소개](#-서비스-소개)
- [🔥 {프로젝트 고유 문구}](#-프로젝트-고유-문구)
  * [{하위 항목}](#하위-항목)
```

### S4 기획 의도

왜 만들었는지를 두세 문장으로. 시장 조사나 통계를 끌어오지 않는다 — 팀이 실제로 겪은 불편을 쓴다.

```markdown
## 💭 이걸 왜 만들었나

{마주친 불편. 구체적인 상황으로}

{그래서 무엇을 만들기로 했는지}
```

## L2 주인공

### T1 기술적 도전 (부트캠프형)

4단 구조. **라벨은 반드시 갈아쓴다** — 원문 라벨을 그대로 쓰면 출처가 드러난다.

```markdown
## 🔥 {프로젝트 고유 문구로 만든 헤딩}

> {이 섹션 전체를 한 줄로}

### [{FE|BE|iOS}] {무엇을 얼마나 개선했는지 수치까지 넣은 제목}

- **{왜 했나}**
    - {마주친 문제. 수치나 증상으로 구체적으로}
- **{뭘 했나}**
    - {시도한 것들. 실패한 시도도 넣으면 훨씬 사람 글이 된다}
- **{어떻게 됐나}**
    - {결과. 전후 수치를 나란히 적는다}
- {더보기 유도 문구는 항목마다 다르게} → [{링크 제목}]({URL})
```

전후 수치가 없으면 이 블록을 켜지 않는다. 수치 없는 기술적 도전은 홍보체가 된다.

**변형 — 위키 요약형.** 부스트캠프 레포에서 흔하다. 본문에는 상황과 질문만 남기고 해결 과정
전체를 위키로 넘긴다. 위키가 이미 있을 때만 쓴다.

```markdown
### {도메인 이모지} {기능 이름}

{어떤 걱정을 마주했고 무엇을 결정했는지 한 단락. 마지막을 질문으로 끝낸다}

→ [{위키 문서 제목}]({위키 URL})
```

### F1 핵심 기능

가장 강한 관용구이고 손으로 짜기 제일 귀찮은 부분이다. 상단 칸에 미디어, 하단 칸에 캡션.

```html
### {기능 묶음 이름}

> {이 묶음을 한 줄로 설명}

<table align="center">
<tr>
  <td><img src="TODO_기능1_GIF" alt="{기능1}"/></td>
  <td><img src="TODO_기능2_GIF" alt="{기능2}"/></td>
</tr>
<tr>
  <td align="center">{기능1 캡션}</td>
  <td align="center">{기능2 캡션}</td>
</tr>
</table>
```

**변형 — 앱 스크린샷.** 모바일은 3~4열로 늘리고 `width`를 280~300으로 줄인다. 웹은 2열,
`width` 480~600.

## L3 본체

### K1 기술 스택

**표 칸에 뱃지를 넣는 혼용형이 기본이다** (기술 스택 섹션이 있는 19개 중 6개로 최다). 역할 칸이 있어 뱃지와
텍스트를 섞어도 자연스럽다. 뱃지 URL·slug·색은 `badges.md`를 읽어서 쓴다.

```markdown
## 🛠 기술 스택

| 역할 | 종류 |
| --- | --- |
| 언어·빌드 | {뱃지} |
| UI | {뱃지} |
| 상태 관리 | {뱃지} |
| 네트워크 | {뱃지} |
| 데이터베이스 | {뱃지} |
| 인프라·CI/CD | {뱃지} |
| 협업 | {뱃지} |
```

**변형 — 영역별 묶음.** 가운데정렬 소제목 + 뱃지 묶음. 마크업은 `badges.md`의 "영역별 묶음".

### A1 아키텍처

다이어그램 뒤에 **왜 이렇게 나눴는지**를 두세 문장. 구성 요소를 나열만 하면 그림과 중복이다.

```markdown
## 🏗 아키텍처

<img src="TODO_아키텍처_다이어그램" alt="시스템 아키텍처"/>

{다이어그램을 두세 문장으로 풀어 설명한다}
```

### A3 폴더 트리 (부트캠프형)

**주석이 핵심이다** — 트리만 있으면 아무 정보가 없다. 50줄을 넘기면 `<details>`로 접는다.

~~~
```text
├── {디렉터리}          # {무엇을 담당하는지 한국어로}
├── core
│   ├── data            # {...}
│   └── domain          # {...}
└── feature
    └── {기능}          # {...}
```
~~~

멀티 모듈이면 트리 위에 모듈 의존 방향을 한 줄로 적는다 — `app → feature → domain → data`.

| 테이블 | 담는 것 |

### R1 실행 방법 (실행 스크립트 있음)

번호 주석 달린 bash 블록. 사전 준비가 있으면 앞에 한 줄로.

~~~
## 📦 실행 방법

**사전 준비**: {Docker Desktop, JDK 21}

```bash
# 1. 의존성 설치
{명령}

# 2. 환경변수 설정
{환경변수 설정 명령}

# 3. 개발 서버 실행
{명령}
```
~~~

`{환경변수 설정 명령}`은 저장소가 실제로 가진 파일로 쓴다 — `.env.example`이 있으면
`cp .env.example .env`, 스프링은 `application-local.yml`, 안드로이드는 `local.properties`,
iOS는 `.xcconfig`. 해당 파일이 없으면 이 단계를 빼고 번호를 다시 매긴다.

확인할 주소가 여러 개면 표로 잇는다. R2가 켜져 있으면 API 문서 주소도 여기 넣는다.

```markdown
| 확인 | URL |
| --- | --- |
| 웹 | http://localhost:{프런트_포트} |
| {문서 이름} | http://localhost:{서버_포트}{문서_경로} |
```

`{문서_경로}`는 스택마다 다르다 — springdoc `/swagger-ui.html`, Ktor `/swagger`,
FastAPI `/docs`. REST Docs는 빌드 산출 정적 HTML이라 로컬 주소가 없다.

### R2 API 명세 (API 문서 있음)

주소와 인증 방식만. 엔드포인트 목록을 README에 옮기지 않는다 — 문서와 어긋나는 순간 거짓이 된다.
`{문서 이름}`은 실제로 쓰는 것으로 — Swagger UI, API 문서, REST Docs.

```markdown
## 📖 API 명세

- [{문서 이름}]({주소}) — {인증이 필요하면 어떻게 얻는지}
```

## L4 사람·규칙

### P1 팀원

아바타 가로 테이블. 파트가 섞이면 헤더에 파트를 적는다.

```markdown
## 👥 팀원

| {파트} | {파트} | {파트} |
| :---: | :---: | :---: |
| <img src="{avatar_url}" width="150"/> | <img src="{avatar_url}" width="150"/> | <img src="{avatar_url}" width="150"/> |
| [{닉네임}](https://github.com/{로그인}) | [{닉네임}](https://github.com/{로그인}) | [{닉네임}](https://github.com/{로그인}) |
| {담당한 것} | {담당한 것} | {담당한 것} |
```

아바타 URL은 `gh api repos/{owner}/{repo}/contributors --jq '.[] | "\(.login) \(.avatar_url)"'` 로
얻어 **통째로 붙인다.** 담당한 것을 사용자에게 못 받았으면 그 행을 지운다 — 커밋 경로로
추측해 채우지 않는다.
`gh`가 없으면 이름만 채우고 아바타 행은 지운다 — `TODO`로 남기면 깨진 이미지가 줄줄이 뜬다.

기여자가 1명이면 표를 쓰지 않고 한 줄로 적는다.

### C1 컨벤션

실제로 지킨 규칙만. 안 지키는 규칙을 적으면 저장소가 거짓말을 한다. 길면 `<details>`로 접는다.

```markdown
## 📌 컨벤션

### 브랜치
- `main` / `develop` / `feat-{이슈번호}-{작업명}`

### 커밋
- `{type}: {한국어 본문}`
- `feat` `fix` `refactor` `docs` `chore` `test`
```

### C2 CI/CD 표 (워크플로 2개 이상)

워크플로 파일을 그대로 읽어 옮긴다. 트리거와 동작을 각각 한 칸으로. 파일명은 확장자까지
그대로 옮긴다 — `.yml`과 `.yaml`이 섞인다.

```markdown
## 🔄 CI/CD

| 워크플로 | 트리거 | 동작 |
| --- | --- | --- |
| `{워크플로_파일명}` | {main 대상 PR} | {lint + test} |
| `{워크플로_파일명}` | {main push} | {이미지 빌드 후 배포} |
```
